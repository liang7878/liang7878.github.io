> **杰文斯悖论 / Jevons Paradox**
> 中文：效率提升不会消灭稀缺，它往往把稀缺重新塑形。
> EN: Efficiency doesn't eliminate scarcity. It often reshapes it.

<!-- more -->

## Question

2023 年以来，单位 token 的推理成本掉了一个数量级又一个数量级。GPT-4 级别的能力，今天的价格大概是发布时的几十分之一。

按直觉，**单价跌了这么多，GPU 的供需压力应该缓解了**——同样一块卡，现在能服务更多请求，那紧张程度该下降才对。

可现实正相反：模型越便宜，H100 越抢不到，云厂商的 GPU 配额越紧，自建集群的人越多。

为什么"更便宜"反而带来"更紧张"？

这不是一个 AI 时代的新问题。150 年前，一个英国经济学家在煤炭身上见过一模一样的剧情。

## Origin

1865 年，威廉·斯坦利·杰文斯（William Stanley Jevons）写了本叫《煤炭问题》（*The Coal Question*）的书。

当时英国正享受蒸汽机效率的飞速提升。瓦特改良的蒸汽机比老式纽科门机省煤得多，烧同样的煤能干更多的活。当时的普遍乐观判断是：**机器越省煤，国家烧的煤就越少，煤会用得更久**。

杰文斯泼了盆冷水。他观察到的事实恰好相反：**蒸汽机越省煤，英国烧的煤总量越大**。

他给出的解释，就是今天我们说的杰文斯悖论。

## Core Idea

把"效率"想成"降价"，整件事就通了。

蒸汽机效率提升，意味着**用蒸汽动力做一件事的成本下降了**。成本一降，原本因为太贵而不划算的用途，突然都变得划算了：工厂用得起蒸汽了、铁路铺得起了、矿井抽水抽得起了。

于是需求不是线性增长，而是**爆炸式扩张**——新场景被解锁的速度，远远超过单位能耗下降的速度。

总消耗 = 单位消耗 × 使用量。效率压低了左边那个因子，却通过降价把右边那个因子撑大了好几倍。两者相乘，总量不降反升。

{% mermaid %}

  A[效率提升] --> B[单位成本下降]
  B --> C[原本不划算的用途变划算]
  C --> D[需求爆炸式扩张]
  D --> E[总消耗不降反升]
  E -.反馈放大.-> C
{% endmermaid %}

关键在那条虚线的反馈：新需求本身又会刺激更多场景被发明出来。这是一个**正反馈循环**，不是一次性的调整。

什么时候会这样？有个前提条件：**需求必须是有弹性的**——也就是降价真的能勾出大量新需求。如果一样东西的需求已经饱和（比如食盐），再便宜也没人多吃，那杰文斯效应就不成立。后面"When It Doesn't Apply"会细说。

## Real-world Example

煤炭只是第一个。这个模式在历史上反复上演：

- **汽车与油耗**：发动机越来越省油，但人们买更大的车、开更远的路、更多家庭买得起车。美国的汽油总消耗并没有因为单车油耗下降而下降。
- **照明**：从蜡烛到白炽灯到 LED，每流明的成本降了几个数量级。结果不是大家照得更省，而是**到处都是光**——城市夜景、广告屏、屏幕。人均照明消耗暴涨。
- **带宽**：单位流量越来越便宜，于是有了 4K 视频、直播、云游戏。没人因为流量变便宜而少用网。

每一次，"效率"都没有省下资源，而是**把资源重新分配到了被新解锁的、更大的需求上**。

## AI Mapping

这才是整篇最重要的部分。把"煤"换成"算力"，剧情一字不差地在 AI 世界重演。

**Inference（推理）**——最直接的对应。token 单价暴跌，于是：
- 以前舍不得用大模型的场景，现在全用上了：每个 PR 自动 review、每条日志自动打标、每个用户消息实时摘要。
- Agent 的兴起更是火上浇油：一个 Agent 任务背后是几十上百次 LLM 调用（推理、反思、工具调用、重试）。**单次调用越便宜，一个任务舍得调用的次数就越多**。
- 结果：总推理量的增长速度，远超单 token 成本的下降速度。**便宜没有省下 GPU，而是把 GPU 喂给了爆炸增长的调用量。**

**AI Infrastructure & GPU Scheduling**——这就是开头那个悖论的答案。模型/推理框架的效率每提升一截（量化、KV-cache 优化、投机解码、更好的 batching），单卡吞吐就上一截，单位成本就降一截——然后需求立刻涌上来把腾出的容量吃光。所以你会观察到：**优化得越好，集群反而越满**。容量规划如果假设"优化 → 闲置 → 可以少买卡"，几乎一定会被打脸。

**Training（训练）**——同样成立但要小心套用。单位 FLOP 成本下降，并没有让大家少花算力，而是直接催生了更大的模型、更长的训练、更多的实验次数。预算省下来的部分，立刻被"那我们再 scale 一截"吃掉。

**Product（产品）**——这是机会面。当某种能力的边际成本趋近于零，**真正的杠杆不在"省着用"，而在"想出原本因为太贵而不可能的新用法"**。第一个意识到"现在每个用户每天可以免费跑 1000 次模型调用"的产品经理，会吃到整整一波红利。

**Evaluation（评估）**——一个反直觉的提醒：推理变便宜，你的 eval 成本也会失控。因为你会忍不住跑更多的评估样本、更多的 A/B、更多的回归。便宜没有让 eval 预算下降，而是让你跑得更频繁。

## Engineering Perspective

同一个杰文斯，不同角色该想到不同的事：

- **如果我是 Infra Engineer**：永远不要把"效率优化省下的容量"当成"可以少买的容量"。优化的真实结果是**需求会涨上来填满**。容量规划要按"解锁的新需求"来算，而不是按"当前负载 ÷ 新效率"来算。给爆发留 headroom。
- **如果我是 Agent Engineer**：单次调用变便宜，会诱导你把 Agent 设计得更"啰嗦"（更多反思、更多重试、更大上下文）。这正是杰文斯在你架构里的化身。要主动设预算上限，否则成本会随能力一起失控。
- **如果我是 PM**：别把降价只用来降毛利。问一个杰文斯式的问题：**"如果这个能力的成本再降 10 倍，会解锁什么今天不可能的产品？"** 红利在新需求侧，不在省钱侧。
- **如果我是 Researcher**：效率类的成果（更省的架构、更快的推理）不会减少算力消耗总量——它们会**抬高所有人的使用基线**。你的高效方法越成功，全行业烧的算力越多。这不是坏事，但要诚实看待它的系统级后果。

## Investment Perspective

杰文斯是理解 AI 算力投资逻辑的一把钥匙，而且它和"AI 便宜了所以卖铲子的不行了"这种直觉正好相反：

```
推理效率提升（更便宜的 token）
        ↓
需求爆炸（更多调用、更多 Agent、更多场景）
        ↓
GPU 需求不降反升 → 云算力需求上升 → 上游（HBM、先进封装、电力）跟着紧张
```

这解释了一个看似矛盾的现象：**模型 API 在疯狂降价的同时，GPU、云、乃至电力却在持续吃紧**。降价不是需求的终点，而是需求的起点。

要绕回 AI 系统设计：这条投资链给工程师的启示是，**算力会长期是稀缺资源**——别指望"等卡便宜了再说"，要把"算力受限"当成系统设计的长期约束，而不是临时困难。

## Life Perspective

生活里也到处是杰文斯：

- **洗碗机**省了你洗一次碗的力气，结果你用更多的碗、更勤地洗——而不是省下时间。
- **更快的通勤**（修了新路）短期省时间，长期却让人搬得更远、通勤总时间不变甚至更长（这就是著名的"诱导需求"）。
- **效率工具**：你用了更快的 IDE、更聪明的补全，结果不是早点下班，而是被期待写更多代码。

绕回 AI：这恰恰是为什么"AI 帮工程师提效"未必让人更轻松——**省下的产能会被更高的预期吃掉**。理解这一点，你才能在设计 AI 工具时，主动去想"我到底是在帮人省时间，还是只是在抬高对他的要求"。

## Misconceptions

最容易误解的一点：

> 杰文斯悖论 ≠ "效率提升**一定**导致总消耗增加"。

它的准确表述是：**在需求有弹性的前提下，效率提升可能导致总消耗增加**。它是"可能"，不是"必然"，而且**依赖条件**。

另一个常见误解：把它当成"所以优化没意义"。恰恰相反——优化非常有意义，它解锁了海量新价值（更多场景、更多产品）。杰文斯说的不是"别优化"，而是"**别指望优化能让你少买资源**"。

## When It Doesn't Apply

杰文斯效应**不成立**的关键条件，是**需求缺乏弹性**——降价勾不出新需求：

- **需求已饱和**：食盐再便宜你也不会多吃。某些内部工具的调用量是固定的，模型再便宜，调用次数也不会涨。这种场景下，效率提升是实打实地省成本。
- **存在硬约束的瓶颈**：如果真正的瓶颈不在你优化的那个环节（比如推理不缺算力、缺的是优质数据或牌照），那优化推理成本并不会引爆需求。
- **监管/配额封顶**：如果用量被外部强制限制（合规、预算硬上限），需求就涨不上去。

判断方法很简单：问一句"**如果这个再便宜 10 倍，会有人想多用吗？**"——如果答案是"会，而且想用的场景多得是"，杰文斯就成立；如果是"不会，就这么多需求"，就不成立。AI 推理显然属于前者，这也是为什么这个悖论在 AI 时代格外刺眼。

## Key Takeaway

> 中文：效率不会消灭稀缺，它只是把稀缺搬个地方。当你让某样东西变得更便宜，先别急着算省了多少——先问问，你即将解锁多大的新需求。
> EN: Efficiency doesn't kill scarcity; it relocates it. When you make something cheaper, don't count the savings first—ask what new demand you're about to unleash.
